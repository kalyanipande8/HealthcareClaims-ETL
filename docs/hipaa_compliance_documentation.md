# HIPAA Compliance Documentation

**Project:** HealthcareClaims-ETL
**Scope:** This document describes the de-identification approach, access
controls, and audit logging actually implemented in this pipeline's code
(`deidentify.py`, `feed_auth.py`, `etl.py`). It is written in the style of
compliance documentation a data engineering team would attach to a
HIPAA-regulated ETL pipeline for internal review / audit.

> **Disclaimer:** This is a portfolio/demo project. All patient data (name,
> date of birth, address) is synthetically generated by
> `simulate_supplier_feeds.py`. No real patient, claim, or covered-entity
> data is used anywhere in this repository. This document demonstrates the
> *pattern* of HIPAA-aware engineering controls, not a certified compliance
> program.

---

## 1. Data Classification

Each unified record (`etl.py: UNIFIED_FIELDS`) is one of two types:

| Type | Contains direct patient identifiers? | Source feeds |
|---|---|---|
| `claim` | Yes, in raw feed (name, DOB, address) | MedPlus, RegionalHealth, SummitCare |
| `supply` | No (pharmacy shipment data only) | PharmaCorp, VitalRx |

Claim records carry Protected Health Information (PHI) as defined under the
HIPAA Privacy Rule (45 CFR §160.103): patient name, date of birth, and
street address are each identifiers on the Safe Harbor list (45 CFR
§164.514(b)(2)). These three fields are treated as PHI from the moment they
are parsed out of a raw feed and are never written to any general-access
output.

## 2. De-identification Approach (`deidentify.py`)

The pipeline applies a Safe-Harbor-inspired de-identification transform to
every claim record **before** it is written to the unified, generally
queryable table (`data/processed/unified_records.csv`):

| Raw PHI field | De-identified replacement | Rationale |
|---|---|---|
| `patient_name` | `patient_token` — `HMAC-SHA256(name\|dob\|address, secret_key)[:16]`, prefixed `PT-` | One-way, keyed pseudonym. Deterministic (same patient -> same token across feeds, enabling cross-supplier linkage for analytics) but not reversible without the secret key, and not a direct identifier itself. |
| `date_of_birth` | `birth_year` — year component only | Matches Safe Harbor's allowance of year of birth (full dates, which could narrow re-identification, are dropped). |
| `address` | `patient_region` — state + 3-digit ZIP prefix (e.g. `NY-142XX`) | Matches Safe Harbor's "initial three digits of ZIP code" generalization; street, city, and full ZIP are dropped entirely and never persisted in any general-access file. |

**Where raw PHI goes:** the fully identified version of each claim record is
written *only* to `data/processed/_restricted_identified_lookup.csv`,
representing a separate, access-controlled store in a real deployment (e.g.
a distinct, encrypted database/table with its own IAM policy and audit
trail, not just a different file in the same bucket). All pipeline logic
downstream of `etl.run_etl()` — data-quality checks, test assertions, and
every file an analyst would normally query — reads only the de-identified
`unified_records.csv`.

**Verification:** `tests/test_pipeline.py::test_deidentification_removes_phi_from_unified_output`
asserts, against the actual generated output, that none of the synthetic
patient names or street names appear anywhere in the de-identified file, and
that every claim record's `birth_year` is generalized to a 4-digit year
(never a full DOB). This is a real, automated check run on every test
invocation — not a documentation claim unverified by code.

## 3. Feed Authentication as an Access Control (`feed_auth.py`)

Before any inbound supplier file is parsed or its PHI touched, the pipeline
enforces a feed-level authentication control:

1. Every supplier signs its feed file with HMAC-SHA256 using a shared secret
   key unique to that supplier (`SUPPLIER_KEYS` in
   `simulate_supplier_feeds.py`, representing keys that in production would
   be issued per trading partner and stored in a secrets manager / HSM).
2. On receipt, `feed_auth.authenticate_feed()` recomputes the HMAC over the
   received bytes and compares it to the supplier's signature using a
   constant-time comparison (`hmac.compare_digest`), preventing
   timing-based signature-forgery attacks.
3. Any file that is unsigned, signed with an unrecognized supplier key, or
   whose signature does not match its (possibly tampered/corrupted) content
   is **quarantined** to `data/rejected/` and never reaches the parsing or
   de-identification stage.

This enforces that only verified, trusted trading partners can introduce
data — including PHI — into the pipeline, and that data altered in transit
(accidentally or maliciously) after signing is detected and rejected rather
than silently ingested. The deliberately-corrupted RegionalHealth batch-2
feed in this repo demonstrates and tests this control end-to-end.

## 4. Access Controls (Implemented Pattern)

This demo runs as a single local process, so there is no multi-user IAM
layer to configure. The pattern it implements, and that a production
deployment would back with real role-based access control, is:

- **Two-tier output separation:** general-access analytics (de-identified
  `unified_records.csv`) vs. restricted PHI lookup
  (`_restricted_identified_lookup.csv`). In production these would be
  separate storage locations/tables with distinct IAM policies, e.g. an
  `analytics-readonly` role that can read the unified table and a narrowly
  scoped `phi-reidentification` role (break-glass only) that can read the
  restricted lookup.
- **Trusted-sender allowlist:** `feed_auth.SUPPLIER_PREFIXES` acts as the
  allowlist of trading partners whose signed feeds the pipeline will accept
  at all — an unrecognized sender's file is rejected regardless of whether
  it is "signed," the same way a real integration layer would reject
  traffic from an unregistered partner.
- **Least-privilege secret scoping:** each supplier has its own HMAC key
  (`SUPPLIER_KEYS`), so compromise of one partner's key does not allow
  forging another partner's feed.

## 5. Audit Logging (`etl.py: run_etl()`)

Every pipeline run appends one row to `logs/audit_log.csv` recording:

`timestamp_utc, actor, action, feeds_authenticated, feeds_rejected, records_loaded, records_flagged`

This is an append-only log (opened in `"a"` mode, header written once) so
prior run history is never overwritten — a basic requirement for HIPAA
§164.312(b) audit control intent (hardware/software/procedural mechanisms
that record and examine activity in systems containing PHI). In production
this would be shipped to a centralized, tamper-evident log store (e.g.
write-once object storage or a SIEM) with the real authenticated
service/user identity as `actor` rather than a static process name.

Separately, `data/processed/dq_summary.json` records, per run: which feeds
were authenticated vs. rejected (and why), per-supplier record counts, and
field-completeness metrics — giving a reviewable trail of exactly what data
entered the system and what was excluded at the authentication boundary.

## 6. Data Quality / Completeness Controls (`etl.py`)

Independent of PHI handling, every unified record is checked for:

- missing or malformed `event_date` (expects `YYYY-MM-DD`)
- missing or non-numeric `amount_or_quantity`
- non-positive or implausibly high (`>$20,000`) claim amounts, flagged as
  outliers for review
- missing `code` (diagnosis code / NDC code)
- missing `record_id`

Flags are recorded per-record in `dq_flags` and aggregated in
`dq_summary.json` (`dq_flag_counts`, `field_completeness` per field). This
gives a concrete, numeric completeness/validity measure for every run,
printed by `run_all.py` and asserted on by the test suite.

## 7. Summary

| HIPAA-relevant control | Implemented as |
|---|---|
| De-identification (Safe Harbor pattern) | `deidentify.py`, applied before any general-access output is written |
| Minimum necessary / data segregation | Separate restricted-identified vs. de-identified output files |
| Access control (sender authentication) | `feed_auth.py` HMAC-SHA256 signature verification per supplier |
| Audit controls | `logs/audit_log.csv` append-only run log + `dq_summary.json` per-run detail |
| Data integrity | Feed authentication rejects tampered/corrupted files before they are parsed |
